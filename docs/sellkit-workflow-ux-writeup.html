SellKit workflow

Workflow and user experience write-up

SellKit is a manual-first BD sourcing workspace for Mariah Rubino. It helps her tune the target profile, review scored prospects with evidence, and prepare outreach packets without automatically sending email, touching LinkedIn, or writing to a CRM.

Scope

Current workflow, Additional Context onboarding, review queue, evidence review, and manual handoff UX.

Mode: Human approval before every send.

1. Tune Mariah's profile Five required onboarding answers plus optional Additional Context.
2. Review the queue Search, filter, sort, and inspect scored targets before taking action.
3. Read evidence Target rationale, score factors, buying committee, signal sources, and email confidence.
4. Approve manually Prepare copy, LinkedIn note, and CRM CSV only after human approval.
1

Start in the review workspace

The first screen keeps Mariah in a work queue, not a marketing page. The top band confirms onboarding status and manual-send policy. The provider architecture is collapsed by default so the highest-frequency action, reviewing targets, is visible immediately.

UX intent

The page assumes Mariah wants to make a decision quickly. High-level provider details are available but not forced into the main path.

2

Use onboarding to calibrate fit, signals, and voice

Edit Onboarding is the control panel for Mariah's preferences. The first five questions remain the required setup. Additional Context is optional and captures everything the structured questions miss: niches, exclusions, regions, deal-size floors, and positioning notes.

What Mariah should enter

  • Strong niches: platform modernization, AI adoption, transformation work, change management.
  • Strong buyer situations: large rollout, executive urgency, senior hiring spike, new initiative owner.
  • Exclusions: regions, sectors, deal sizes, industries, title patterns, or accounts to avoid.

What the app does with it

  • Treats it as calibration data for fit and tone.
  • Stores changes in an append-only history table.
  • Never treats context as permission to send, enrich, or automate LinkedIn.
3

Save context, then choose whether to re-score

When Additional Context changes, SellKit does not spend provider credits automatically. Instead, it marks the queue as potentially stale and asks Mariah whether to re-score. This keeps cost and workflow control with the human operator.

Important behavior

The button is intentionally manual. In this phase it is a no-spend stub that marks the local queue current. A later persisted scoring job can attach the same UX to a real re-score run.

4

Review one target at a time with evidence visible

The central review panel explains why the selected person is worth considering. Mariah can inspect the company fit, buyer fit, review gate, verified email, and checklist before approving anything. The outreach packet is visible on large screens so the decision and draft stay connected.

Area What Mariah learns UX purpose
Queue Who is available for review, score, status, company, and recency. Fast triage without opening each target.
Why this target The specific signal and expert-services angle. Shows the outreach reason in plain language.
Review checklist Account fit, buyer fit, signal evidence, email confidence, draft readiness. Prevents approval from becoming a blind click.
Outreach packet Email, LinkedIn note, CRM export status, and approval state. Keeps handoff actions tied to the reviewed evidence.
5

Approve draft, but keep sends manual

Approval changes the target state and unlocks the manual CRM export path. Email copy and .eml download remain blocked until approved sender footer details are configured. This makes the product usable in a policy-constrained environment without hiding the missing setup.

Manual-first guardrail

SellKit prepares approved work for Mariah to review and move manually. It does not send email, automate LinkedIn, or write to Salesforce from this flow.

6

Mobile keeps the same workflow readable

The mobile layout stacks the form and turns the queue into cards. The Additional Context field remains usable, the counter stays visible, and no horizontal scrolling is introduced.

7

UX assessment and recommended improvements

The current experience is coherent for a human-in-the-loop operator. The strongest pieces are the collapsed provider architecture, visible manual-send status, review checklist, and evidence-first packet. A few small changes would make it easier for a nontechnical user.

Working well

  • The first screen is a work queue, not a landing page.
  • Mariah can tune targeting in plain English.
  • Context changes do not trigger automatic spend.
  • The app separates approval, email copy, and CRM export.
  • Evidence and draft live close together on desktop.

Recommended next refinements

  • Rename Re-score queue to Mark scores current while it remains a V1 stub.
  • Add a tiny setup health panel for sender footer, provider keys, CRM policy, and approved domain.
  • Add an "Example context" shortcut next to the textarea for nontechnical users.
  • Show when context was last saved and who changed it.
  • When real persisted scoring is wired, show estimated cost before re-score starts.
8

Data and guardrail model

Additional Context is intentionally designed as calibration, not instruction. The backend stores the latest context on the onboarding profile and writes every text change to history. Score versioning fields are ready for persisted scoring, but the current user flow does not trigger provider spend automatically.

Object Purpose User impact
context_text Latest optional onboarding context, up to 2,000 characters. Lets Mariah add nuance without changing the five required questions.
context_source Tracks whether context came from manual entry, guide paste, or future API import. Keeps future "Send to SellKit" paths auditable.
onboarding_context_history Append-only record of context changes. Supports review and rollback conversations without overwriting history.
context_version Version/hash a score can be stamped with when persisted scoring is wired. Explains why older scores may need review after context changes.
